# SKILLEZO Backend — API Conventions

This document outlines the design conventions and data type standards enforced by the SKILLEZO backend API.

---

## 1. HTTP Verbs & Semantics

| HTTP Verb | Purpose | Idempotent | Body Allowed | Expected Response |
| :--- | :--- | :--- | :--- | :--- |
| `GET` | Retrieve single or multiple resources. | Yes | No | `200 OK` |
| `POST` | Create a new domain entity. | No | Yes | `201 Created` |
| `PATCH` | Update specific fields of an existing entity. | No | Yes | `200 OK` |
| `DELETE` | Remove a resource. | Yes | No | `200 OK` or `204 No Content` |

---

## 2. Resource Naming & URL Structure

* **Plural Nouns**: Resource paths use plural nouns (e.g., `/api/companies`, `/api/profile`).
* **Kebab-Case Routes**: URL paths use lowercase kebab-case (e.g., `/api/me/target-role`).
* **The `/me` Pattern**: Routes targeting the authenticated user's active context use `/me` (e.g., `GET /api/profile/me`, `GET /api/companies/me`).
* **Route Order Precedence**: Fixed `/me` routes are registered **BEFORE** parameter routes (`/:companyId`) in Express routers to prevent Express from parsing `me` as an ID parameter.

---

## 3. ID Distinction Standard

> [!IMPORTANT]
> The backend distinguishes between **Better Auth User IDs** and **MongoDB Entity ObjectIds**:

1. **User ID (`userId`, `createdBy`, `invitedBy`)**:
   - **Type**: `string`
   - **Origin**: Generated by Better Auth session authentication system.
   - **Validation**: Verified by `requireAuth` middleware. Do **NOT** validate user IDs with MongoDB `ObjectId` validators.
2. **Domain Entity ID (`companyId`, `profileId`, `roleId`)**:
   - **Type**: 24-character hexadecimal MongoDB `ObjectId` string.
   - **Validation**: Enforced via `objectIdSchema` (`z.string().regex(/^[0-9a-fA-F]{24}$/)`).

---

## 4. Date & Time Format

All timestamps returned by the API follow the **ISO-8601 UTC** standard format:

```
YYYY-MM-DDTHH:mm:ss.sssZ
Example: "2026-08-11T07:38:00.000Z"
```

* **Input Dates**: For fields accepting dates (e.g. `startDate`, `endDate`), the frontend may supply ISO strings or standard date strings. The backend parses them using `z.coerce.date()`.

---

## 5. Nullable vs Optional Fields

* **Optional Fields (`field?: type`)**: May be omitted from the request body payload. If omitted during a `PATCH` request, the field's current stored value remains unchanged.
* **Nullable Fields (`field: type | null`)**: Can be explicitly set to `null` by the client to clear or reset the stored value in the database.

---

## 6. Response Headers

All API responses include standard JSON headers:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Access-Control-Allow-Credentials: true
```
