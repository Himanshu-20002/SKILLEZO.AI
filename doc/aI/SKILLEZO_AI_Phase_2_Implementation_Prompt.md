# SKILLEZO AI — PHASE 2 IMPLEMENTATION PROMPT
## Evidence Layer & Candidate Context Snapshot Caching

You are working on the SKILLEZO AI Career Intelligence Platform.

Phase 1 — AI Gateway & Provider Abstraction — is already COMPLETE and verified.

**DO NOT redo Phase 1.**

Your only task is to implement **PHASE 2: Evidence Layer & Candidate Context Snapshot Caching**.

---

## 1. Objective

Build a production-grade Evidence Layer that converts SKILLEZO's existing deterministic intelligence into a **Verified Candidate Evidence Bundle**, then builds a **Candidate Context Snapshot** that can be efficiently cached and reused by the future AI Orchestrator.

The LLM must **NOT** become the source of truth. Existing deterministic SKILLEZO engines remain authoritative.

Architecture:

```text
Existing Candidate Data
        ↓
Deterministic Intelligence Engines
        ↓
Evidence Collector
        ↓
Evidence Validator
        ↓
Evidence Normalizer
        ↓
Verified Candidate Evidence Bundle
        ↓
Candidate Context Composer
        ↓
Candidate Context Snapshot
        ↓
Cache
```

---

## 2. Critical Architectural Rules

### Deterministic intelligence is authoritative

Never allow an LLM to calculate or overwrite:

- ATS scores
- Role/JD match scores
- Impact/content scores
- Skill gaps
- Employability metrics
- Resume intelligence metrics
- Matching scores
- Career intelligence metrics generated by deterministic engines

AI may explain, summarize, reason over, prioritize, and recommend, but it cannot change deterministic values.

---

## 3. Evidence Provenance

Every evidence item must explicitly identify provenance.

```ts
export type EvidenceType =
  | "DETERMINISTIC"
  | "EXTRACTED"
  | "AI_GENERATED";

export type VerificationStatus =
  | "VERIFIED"
  | "UNVERIFIED"
  | "REVIEW_REQUIRED";
```

Deterministic engine output must use:

```ts
evidenceType: "DETERMINISTIC"
verificationStatus: "VERIFIED"
```

The validator must prevent AI-generated content from masquerading as deterministic evidence.

## 6. Authenticated Candidate Ownership

Candidate identity must come from the authenticated server context.

Never trust:

```text
model → userId
request body → userId
```

Use the existing authenticated identity/context, such as:

```ts
req.user.id
```

Every candidate-specific repository/service lookup must verify ownership.

If an entity ID such as a resume or job is supplied, validate that the entity belongs to the authenticated candidate before returning data.

The future model must never control candidate identity.

## 7. Evidence Validator

The Evidence Validator must be an **ACTIVE validation layer**, not a pass-through.

Validate:

### Required fields

- `id`
- `sourceEngine`
- `metric`
- `value`
- `evidenceType`
- `verificationStatus`
- `extractedAt`

### Provenance consistency

Reject contradictory or unsupported provenance combinations.

### Deterministic protection

If:

```ts
evidenceType === "DETERMINISTIC"
```

the value must originate from an approved deterministic engine.

Never accept arbitrary model-generated deterministic values.

### Value validation

Reject:

- undefined values
- malformed evidence
- invalid numeric metrics
- invalid score ranges
- malformed source identifiers
- unsupported evidence types
- unsupported verification states

Use Zod if consistent with the existing architecture.

